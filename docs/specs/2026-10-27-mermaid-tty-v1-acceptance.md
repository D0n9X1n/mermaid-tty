# mermaid-tty v1 acceptance tests (normative)

This file lists the acceptance checks for spec A ([`…-design.md`](2026-10-27-mermaid-tty-v1-design.md)) and spec B ([`…-docs-release.md`](2026-10-27-mermaid-tty-v1-docs-release.md)). Spec C's per-type checks are in [`…-diagram-matrix.md`](2026-10-27-mermaid-tty-v1-diagram-matrix.md).

Every row is a must-pass check that CI runs: `.github/workflows/ci.yml`, on Linux, macOS and Windows, for every push and pull request, mostly through `scripts/check.sh`. Parts labeled otherwise:
- **Release:** runs in `release.yml` on a `v*` tag;
- a label ending in **review**: a judgment recorded in `docs/reviews/`. CI still runs its objective parts. Each verdict file lists every reviewed file with its SHA-256, and CI fails when a reviewed file no longer matches.

## Spec A

| ID | Requirement | Check |
|---|---|---|
| A1 | Flowchart syntax | There is one fixture per feature in requirement 1: each shape, edge kind, edge end and label form; chains; `&`; nested subgraphs with `direction`; comments; the frontmatter title; and the ignored directives. Each fixture renders and validates at 60, 80 and 120 columns and matches its golden snapshot. |
| A2 | Sequence syntax | There is one fixture per feature in requirement 2. Each is checked the same way as in A1. |
| A3 | Flat nodes | For every shape: a one-line label renders as exactly 1 row; a `<br/>` label with N lines renders as N rows; a wrapped label takes as many rows as it has wrapped lines. No row of a node consists only of border glyphs. Under the mono theme, which has no color, every pair of shapes has different end caps. |
| A4 | Width | **Width table:** ASCII counts 1; `中`, `ア` and `한` count 2; `─`, `│`, `┌`, `◇` and `▶` count 1; `e`+U+0301 counts 1; ZWSP counts 0. Text containing ZWJ, VS15/VS16, regional indicators, emoji modifiers or control characters is unsupported, and the diagram falls back. **Fit ladder:** each step (tighter gaps, wrapped labels, LR→TD) has a fixture sized so that this step is the first one that fits, and the test asserts which step was taken. A width below the minimum falls back. |
| A5 | Fail closed | **Mutation tests:** the validator receives a hand-broken layout for each invariant, and each must fail. The broken layouts are: a missing label instance, a duplicated label instance, a disconnected edge end, an overwritten glyph, and an overlong row. Distinct nodes with identical text pass, because instances are counted by node id. **Errors:** parse errors and unsupported types return `null`, and the hook then draws the original fence. The reason is logged only at debug level; the test asserts that nothing extra appears in the drawn tree. |
| A6 | Source preserved | **Hook tests:** cover prose, then a diagram, then prose; two adjacent fences; a fence between two paragraphs; and a reply with CRLF line endings. The prose reaches `next()` unchanged and the diagrams render in order. An unclosed fence is passed to `next(e)` untouched, and so is any reply on a non-terminal surface. **Command:** `/mermaid-tty source` and `/mermaid-tty diagram` set the mode in `$.state` and invalidate the drawing; in source mode the hook passes every reply to `next(e)` untouched; bare `/mermaid-tty` reports the mode. **In Claude Code:** see A9. |
| A7 | Colors | Unit tests assert the color of each of the 7 roles under the default mapping (theme keys) and under each of the 5 palettes. A hook test asserts that the drawn spans carry those colors. |
| A8 | Zero install | **Portability:** (`scripts/check-portable.ts`) `package.json` has no `dependencies`. Every import under `core/` and `hooks/` is relative, except type-only `claude-code` imports. The code uses none of: `node:` imports, `require`, `process`, `Buffer`, `document`, `window`, `eval`, `new Function`, or dynamic `import()`. **Benchmark:** (`scripts/bench.ts`) renders each corpus or fixture diagram 20 times, cold, at 80 columns, and reports p50 and p90 together with the machine and Node version. p90 must be 50 ms or less on the development Mac; in CI, on each OS, it fails above 200 ms, which catches algorithmic regressions without timing flakes. **Cache:** an LRU of 64 entries, keyed by (text, width, theme). Tests cover a hit; a miss whenever any part of the key changes; and eviction of the least recently used entry when a 65th is added. **No build:** in a fresh `git clone` of the commit, with no `npm install` and no build step, `node --test`, `claude plugin test .` and `scripts/smoke.ts` all pass. `scripts/smoke.ts` renders a flowchart fixture through `core/render.ts` from the checked-in sources. **Validation:** `claude plugin validate .` passes. **Platforms:** CI runs `scripts/check.sh` on Linux, macOS and Windows. `.gitattributes` keeps text files LF, so goldens compare byte for byte. Every glyph the renderer emits, outside source text, comes from one allow-list in `core/glyphs.ts`: the set the matrix's common rule 12 allows. No non-ASCII glyph in it has the Unicode `Emoji` property (so `►`/`◄`, never `▶`/`◀`, which some terminals draw as wide emoji); a test scans every golden. |
| A9 | End to end | **Harness:** `scripts/e2e/` runs as a separate CI job on all three OSes: real Claude Code (the pinned version; the scheduled job tests each new release) loads the repo with `--plugin-dir`, in a fresh config, against a mock Messages API (`ANTHROPIC_BASE_URL`; no account or secret), driven through a pseudo-terminal at 100 columns. The mock replies with prose, a CJK flowchart, a sequence diagram, an unsupported diagram and an unclosed fence. Reading the reconstructed screen and its colors, the test asserts: each diagram is drawn as themed rows, in truecolor under the default mapping and the colored palettes, and with no color under mono (A3); the prose is intact; the unsupported and unclosed fences show their source; after `/mermaid-tty source` every diagram, on screen and under ctrl+o, shows its Mermaid source; and `/mermaid-tty diagram` draws them again. **Stored:** the session transcript the run writes holds the mock's reply byte for byte, and `/copy` hands the exact fence body to a stub clipboard command (`pbcopy` on macOS, and on each other OS whose clipboard command can be stubbed; the job reports which OSes ran it). It runs once with the default mapping, once per curated theme through `userConfig`, and once with truecolor unavailable, where the diagram rows carry 256-color codes (`38;5;n`). **Release:** `release.yml` repeats it on the copy installed from the marketplace. |
| A10 | Corpus | `fixtures/corpus/` holds at least 90 synthetic blocks with the owner's feature mix: mostly flowchart and graph, plus sequence, with quoted labels, edge labels, CJK, `<br/>`, subgraphs and frontmatter. Every block renders and validates at 80 and 120 columns. On the development Mac the same test also takes a path to the owner's 87 private blocks, which are never committed. |

## Visual review (*review*, for A and C)

**Gallery:** every golden, rendered to PNG at 80 columns, at 60 columns, and with CJK labels.

**In CI:** `scripts/render-gallery.ts` renders the gallery as SVG and uploads it as a build artifact. `scripts/check-tangle.ts` checks the four tangle rules below on every golden's role map. Each curated palette's role colors have a contrast ratio of at least 3:1 against its background, and differ pairwise by at least 0.08 in OKLab; mono is exempt from the color checks, because it tells roles apart by glyphs and caps.

**Reviewers:** the PM inspects the PNGs. A cross-family reviewer inspects the text and the role map.

**Tangled:** a diagram is tangled if any of these is true:
- an edge passes through a node;
- two edges share a segment but share no endpoint;
- an edge's direction is ambiguous, because its arrowhead is missing or sits on a junction;
- an edge label is not adjacent to its edge.

**Passes:** a diagram passes when every label is readable, it is not tangled, and its colors tell the roles apart.

## Spec B

| ID | Requirement | Check |
|---|---|---|
| B1 | README | **Docs check:** `scripts/check-docs.ts` asserts: the hero has the logo image and tagline; the CI, release, license and stars badges are present; the exact two-line install block is present; the Before/after, Themes, Configuration and FAQ sections exist, with the FAQ covering fallback, width and CJK; the wiki links (English and 简体中文) are present; every `assets/` image exists and matches a fresh `render-svg` run; in each SVG, every glyph's `x` equals its column × cell width. **Beauty review:** the PM reviews the rendered GitHub page. |
| B2 | Wiki pages | All five named pairs exist. Each pair has the same heading levels in the same order. Each page opens with exactly one link to its twin, which is the only cross-language link. zh-CN bodies contain CJK prose; English bodies contain none outside code. **Per paragraph:** every non-code paragraph of a zh-CN page contains CJK characters, so a mostly untranslated page fails. **Translation review:** the PM and a cross-family reviewer confirm that each of the five pairs says the same things in full, and record the verdict in `docs/reviews/`. |
| B3 | Publishing | **Publish test:** `scripts/test-wiki-publish.sh`, run in throwaway repos, covers: mirroring, a no-op run, and removal of stale pages. **Workflow check:** `check-docs.ts` asserts the workflow's triggers (`push` to `main` and `workflow_dispatch`), the job-scoped `contents: write` permission, and SHA-pinned actions. **Release:** the workflow run on `main` succeeds and the wiki shows the pages. If the wiki repo doesn't exist yet, the one-click bootstrap is reported to the owner and the run is repeated. |
| B4 | CI | `check-docs.ts` asserts that `ci.yml`: runs on push and pull_request; runs a matrix of ubuntu-latest, macos-latest and windows-latest; pins actions by SHA; sets up Node 24 and Claude Code; runs `scripts/check.sh` and the A9 end-to-end job; and has a scheduled job that runs A9 against every newly published Claude Code version. It also asserts `release.yml`'s `v*` trigger and SHA pins, and that every step running a `.sh` script sets `shell: bash` (Git Bash on Windows). `scripts/check.sh` runs under `set -euo pipefail`, so any failing command, including the native Windows `claude plugin validate` and `claude plugin test`, fails the job. The PR's CI run is green on all three. |
| B5 | Release | **Every PR:** CI registers the local marketplace (`claude plugin marketplace add ./`), installs the plugin from it (`claude plugin install mermaid-tty@mermaid-tty`) and finds it in `claude plugin list`, which catches `marketplace.json` mistakes before release. **Release:** on the `v1.0.0` tag, `release.yml` checks that the tag matches `plugin.json`'s version and that the release notes contain both install commands, installs the plugin from the GitHub marketplace into a fresh config, and runs A9 against the installed copy. |
| B6 | Icon | `scripts/make-icon.sh` produces `.claude-plugin/icon.png` from `assets/icon.svg`. The PNG is 512×512, read from its header (`sips` confirms on the Mac), and under 2 MB. |
| B7 | CI coverage | **Check IDs:** each row ID (A1–A10, B1–B7); one ID per bold label inside a row, formed as the row ID, a dot and the label's slug (`A8.portability`, `A8.no-build`, …); and one ID per bold label in the visual-review section, formed as `VR.` and the slug (`VR.gallery`, `VR.in-ci`, …). Every label is bold text ending in a colon inside the bold. A slug is the label lowercased, with each run of characters other than `a`–`z` and `0`–`9` turned into one `-`, and `-` trimmed from both ends. IDs of labels that define a human judgment (`VR.reviewers`, `VR.passes`, `B1.beauty-review`, `B2.translation-review`) map to the step that checks the verdicts' hashes. `ci/coverage.json` maps every check ID to the `id:` of a step in `ci.yml` or `release.yml`. `scripts/check-ci-coverage.ts`, run by `check.sh`, parses the IDs from this file and fails if an ID has no step, a mapped step `id:` is missing from the workflows, or the manifest names an unknown ID. |
